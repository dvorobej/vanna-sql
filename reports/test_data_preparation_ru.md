# Подготовка тестовых данных

## Цель

Перед оценкой поиска и генерации SQL нужен **контролируемый набор примеров**: описания аналитических задач на естественном языке, эталонные SQL-запросы и таблицы результатов их выполнения. Этот документ описывает, как такой набор создаётся с помощью языковой модели на основе уже подготовленной базы данных и текстового описания её схемы.

Подготовка данных — отдельный этап от самой оценки системы. Сначала формируется корпус примеров; затем он используется в экспериментах по поиску и генерации.

## Что получается на выходе

В результате пайплайна для каждой базы данных появляются связанные артефакты:

| Артефакт | Назначение |
|----------|------------|
| Таблица с исходными описаниями запросов | Первичные формулировки задач с уровнем сложности и уникальным идентификатором |
| Эталонные SQL-скрипты | Один скрипт на каждый успешно сгенерированный пример |
| Эталонные таблицы результатов | Результат выполнения SQL — основа для оценки генерации |
| Таблица с переписанными описаниями | Три стиля формулировки (краткий, бизнес-, технический) для каждого примера |
| Таблица с related-описаниями | Перефразированные варианты запросов для проверки устойчивости поиска |

Каждый пример сквозным образом связан **идентификатором (uuid)**: один и тот же uuid проходит через все этапы и связывает описание, SQL и результат.

## Предварительные условия

Пайплайн предполагает, что для выбранной базы уже есть:

- **SQLite-база с тестовыми данными** — реальная база, на которой можно выполнять запросы;
- **Текстовое описание схемы** — человекочитаемое представление таблиц, полей и комментариев в выбранном формате (inline или yaml) и варианте подробности (краткий, бизнес-, технический).

Описание схемы задаёт контекст для языковой модели: какие таблицы существуют, что означают поля, какие связи между сущностями возможны. Без этого модель не сможет генерировать осмысленные задачи и SQL.

## Общая схема пайплайна

```text
1. Сгенерировать описания аналитических задач (по уровням сложности)
2. Для каждого описания — сгенерировать SQL, выполнить, сохранить результат
3. Переписать описания в три стиля (краткий / бизнес / технический)
4. Для каждого стиля — сгенерировать несколько related-перефразировок
```

Каждый следующий шаг опирается на результат предыдущего.

## Шаг 1. Генерация описаний запросов

Языковая модель получает текстовое описание схемы базы и для каждого запроса генерирует **формулировку аналитической задачи** на русском языке.

### Уровни сложности

Задачи распределяются по трём уровням:

| Уровень | Характер задач |
|---------|----------------|
| **easy** | Простые выборки, фильтрация по одному-двум условиям, базовые агрегаты |
| **medium** | Соединения таблиц, группировки, несколько условий, сортировка |
| **hard** | Сложные соединения, подзапросы, оконные функции, многошаговая логика |

Число задач на каждый уровень задаётся явно (например, по 40 easy, medium и hard — всего 120 примеров).

### Что сохраняется

Для каждой сгенерированной задачи фиксируются:

- имя базы данных;
- текст описания;
- уровень сложности;
- уникальный uuid.

Исходное описание попадает в колонку с базовой формулировкой запроса — она используется на следующем шаге для генерации SQL и позже как отправная точка для переписывания в другие стили.

## Шаг 2. Генерация SQL и эталонных результатов

Для **каждой строки** таблицы с описаниями модель генерирует SQL-запрос, который должен ответить на поставленную задачу.

### Процесс для одного примера

1. Модель получает описание схемы, текст задачи и уровень сложности.
2. Генерируется SQL; из ответа извлекается исполняемый фрагмент (SELECT, WITH или аналог).
3. Проверяется, что запрос **только для чтения** — допускаются SELECT и WITH, запрещены изменения данных и DDL.
4. SQL выполняется на подключённой SQLite-базе.
5. При успешном выполнении с **непустым** результатом таблица нормализуется и сохраняется вместе со скриптом.

### Нормализация результата

Перед сохранением таблица приводится к каноническому виду:

- столбцы сортируются по алфавиту;
- строки сортируются по всем столбцам;
- индекс сбрасывается.

Это обеспечивает согласованное сравнение результатов на этапе оценки генерации.

### Отбор успешных примеров

Не каждый сгенерированный SQL попадает в итоговый корпус. Пример **отбрасывается**, если:

- SQL не прошёл проверку read-only;
- выполнение завершилось ошибкой;
- запрос вернул пустую таблицу.

По итогам прогона собирается сводка: сколько примеров обработано, сколько SQL сгенерировано, сколько успешно сохранено, сколько отброшено по каждой причине. Только примеры с сохранённым SQL и результатом участвуют в последующей оценке.

## Шаг 3. Переписывание описаний в три стиля

Исходные формулировки из шага 1 переписываются в **три стиля**, сохраняя смысл задачи:

| Стиль | Смысл |
|-------|--------|
| **Краткий** | Лаконичная формулировка, минимум деталей |
| **Бизнес** | Язык предметной области, акцент на бизнес-вопросе |
| **Технический** | Более формальная формулировка с опорой на структуру данных |

Для каждого стиля модель получает **соответствующее описание схемы** (краткое, бизнес- или техническое) — так стиль формулировки согласован с тем, как представлена база. Смысл и сложность исходной задачи не меняются; меняется только способ изложения.

На выходе одна строка на uuid дополняется тремя колонками с переписанными описаниями. Эта таблица используется при оценке генерации (разные стили запроса) и как основа для related-вариантов.

## Шаг 4. Генерация related-описаний

На последнем шаге для **каждого стиля** переписанного описания создаются **несколько перефразировок** — альтернативные формулировки той же задачи, которые пользователь мог бы задать иначе.

### Как устроен результат

- Для каждого uuid и каждого стиля генерируется заданное число вариантов (например, три).
- Каждый вариант попадает в отдельную related-колонку (краткая, бизнес-, техническая перефразировка).
- Исходная строка **размножается**: одна задача превращается в несколько строк с индексом варианта, чтобы related-формулировки не смешивались в одной записи.

Related-описания нужны прежде всего для **оценки поиска**: проверяется, находит ли система правильный SQL-пример, когда пользователь спрашивает не теми словами, под которыми пример был проиндексирован.

### Роль описания схемы

Как и при переписывании, для каждого стиля используется своё текстовое описание схемы. Модель опирается на него, чтобы перефразировка оставалась правдоподобной относительно структуры базы, а не сводилась к чистой синонимической замене слов.

## Настраиваемые параметры

| Параметр | Что влияет |
|----------|------------|
| База данных и вариант SQLite | На каких данных выполняются эталонные запросы |
| Описание схемы (стиль комментариев, вариант подробности) | Контекст для генерации задач и SQL на первых шагах |
| Распределение по сложности | Сколько easy / medium / hard задач в датасете |
| Модель для генерации задач и SQL | Качество и разнообразие первичного корпуса |
| Температура генерации SQL | Детерминированность эталонных скриптов (низкая температура — более стабильный SQL) |
| Модель для переписывания | Качество стилевых вариантов описаний |
| Модель для related-вариантов | Разнообразие перефразировок для оценки поиска |
| Число related-вариантов на стиль | Объём данных для тестов устойчивости поиска |

## Связь с оценкой системы

Подготовленные данные питают два независимых направления экспериментов:

| Направление | Какие артефакты используются |
|-------------|------------------------------|
| **Оценка поиска** | Переписанные и related-описания + эталонные SQL; проверяется, находится ли правильный пример в top-k |
| **Оценка генерации** | Описания (в разных стилях) + эталонные таблицы результатов; проверяется, совпадает ли таблица от сгенерированного SQL с эталоном |

Эталонные SQL и результаты выполнения служат **золотым стандартом**: для поиска — как связка «описание → правильный пример», для генерации — как эталонный ответ на задачу.

## Ограничения

- Качество датасета **полностью зависит от языковой модели** и от точности описания схемы. Ошибки в схеме или в SQL на этапе подготовки переносятся в оценку.
- В корпус попадают только примеры с **непустым успешным результатом**. Сложные задачи отсеиваются чаще — возможен перекос в сторону более простых запросов.
- Эталонный SQL не обязан быть единственным правильным решением; эталоном считается **конкретная таблица**, полученная от сохранённого скрипта.
- Related-варианты могут слегка смещать акцент формулировки; они предназначены для проверки поиска, а не как альтернативные эталоны для генерации.
- Пайплайн ресурсоёмкий: для сотен задач требуются сотни вызовов LLM на каждом шаге, особенно при генерации related-описаний для всех стилей и вариантов.
