# Оценка качества поиска

## Цель

Мы проверяем, может ли векторное хранилище **найти правильный SQL-пример** по описанию запроса на естественном языке. Качество поиска формулируется как **задача ранжирования**: для каждого запроса известен эталонный пример, и мы смотрим, попадает ли он в top-k выдачи.

Генерация SQL в этой оценке **не участвует** — система только ищет похожие уже сохранённые пары «описание — SQL».

## Что мы тестируем

На качество поиска влияют:

- **Стиль описания**, в котором примеры проиндексированы в хранилище (краткий, бизнес- или технический);
- **Формулировка запроса при поиске** — в том числе перефразированные и расширенные варианты (related-описания), отличающиеся от текста, под которым пример был сохранён.

Так можно проверить, насколько поиск устойчив к тому, что пользователь спрашивает иначе, чем сформулировано описание в корпусе.

## Входные данные

| Данные | Назначение |
|--------|------------|
| Таблица с описаниями и их вариантами | Тексты запросов, метаданные, related-формулировки |
| Эталонные SQL-скрипты | SQL, сопоставленный каждому примеру |

Перед оценкой:

- остаются только строки, для которых существует эталонный SQL;
- дубликаты пар «идентификатор — описание — SQL» удаляются, чтобы каждый уникальный пример попал в индекс один раз.

### Два типа текстов запроса

- **Текст для индексации** — описание в одном из стилей (краткий / бизнес / технический); именно под ним пример сохраняется в хранилище.
- **Тексты для поиска** — по умолчанию три related-колонки (краткая, бизнес- и техническая перефразировка). Для каждой из них отдельно измеряется, находится ли правильный пример.

## Пайплайн оценки

Оценка выполняется **отдельно для каждого стиля описания** (краткий, бизнес-, технический):

1. **Подготовка корпуса** — загрузка описаний, фильтрация по наличию SQL, удаление дубликатов.
2. **Сброс хранилища** (опционально) — очистка коллекций схем и примеров перед новым прогоном.
3. **Инициализация** — подключение к векторному хранилищу, модели эмбеддингов и базе SQLite.
4. **Загрузка DDL** — схемы таблиц в выбранном формате комментариев.
5. **Загрузка примеров** — пары «описание — SQL»; для каждого примера запоминается идентификатор точки в хранилище как эталон для последующей проверки.
6. **Поиск** — для каждой строки датасета и каждой формулировки запроса запрашивается top-k похожих примеров.
7. **Сохранение предсказаний** — для каждой формулировки сохраняется упорядоченный список найденных идентификаторов.

### Поведение эмбеддингов

При поиске в векторное представление попадает **только текст запроса**, без SQL. Это соответствует пользовательскому сценарию: человек задаёт вопрос словами, а релевантность должна определяться смыслом описания, а не синтаксисом SQL.

## Метрики

По сохранённым результатам поиска считаются агрегированные метрики ранжирования **отдельно для каждой формулировки запроса** и **в сводном режиме**.

Для каждой строки:

- **Эталон** — идентификатор правильного примера в хранилище для данного примера и стиля описания.
- **Предсказание** — упорядоченный список идентификаторов из выдачи top-k.

### Определения метрик

| Метрика | Смысл |
|---------|--------|
| **MRR** (средний обратный ранг) | Среднее значение 1 / rank, где rank — позиция первого появления эталона; 0, если эталон не найден |
| **MAP@k** (средняя точность на top-k) | Среднее 1 / rank, если эталон попал в top-k; иначе 0 |
| **Recall@k** | Доля запросов, где эталон встречается где-либо в top-k |

### Сводный режим (combined)

Сводная метрика строится не путём слияния списков выдачи, а **усреднением оценок по всем формулировкам запроса**: для каждой пары «пример × формулировка» считается отдельный вклад в MRR / MAP@k / Recall@k, затем значения объединяются. Так оценивается общая устойчивость поиска при разных способах задать тот же вопрос.

Отдельно можно считать **соответствующий режим (respective)**: для каждого стиля описания в индексе используется только выдача по related-формулировке того же стиля (краткая к краткой, бизнес к бизнес и т.д.).

### Как интерпретировать результаты

- Высокий **Recall@k** — правильный пример обычно попадает в top-k.
- **MRR** и **MAP@k** сильнее штрафуют случаи, когда верный ответ есть, но низко в списке.
- Сравнение стилей описания показывает, при какой формулировке примеры легче находить.
- Сравнение related-формулировок показывает устойчивость к перефразированию.
- Сводный режим даёт общую картину по всем вариантам запроса; respective — картину «стиль к стилю».

## Настраиваемые параметры

| Параметр | Что влияет |
|----------|------------|
| Стили описания для индексации | Под каким текстом примеры попадают в хранилище |
| Формат комментариев DDL | Как схема представлена при загрузке |
| Вариант подробности комментариев к схеме | Насколько развёрнуто описаны таблицы и поля |
| Глубина выдачи k | Сколько ближайших соседей запрашивается и до какого rank считаются метрики |
| Набор формулировок для поиска | Какие перефразировки участвуют в оценке |
| Сброс хранилища | Чистый прогон без данных предыдущих экспериментов |

## Ограничения

- Для каждого запроса предполагается **ровно один релевантный документ** — канонический пример для данного идентификатора и стиля описания.
- Поиск оценивается на **полностью заполненном** корпусе (все примеры в хранилище), в отличие от генерации, где используется кросс-валидация.
- В оценку попадают только примеры с заранее сгенерированными SQL-скриптами.
- Метрики отражают качество **поиска примера**, а не корректность сгенерированного SQL.
