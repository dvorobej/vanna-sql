# Поиск и генерация SQL с использованием Vanna и векторного хранилища

## 1. Цель решения

Цель проекта — построить прототип системы, которая помогает пользователю на естественном языке находить релевантные SQL-скрипты и генерировать новые SQL-запросы к базе данных. В качестве ядра используется Vanna: она объединяет векторное хранилище, большую языковую модель и подключение к реальной базе данных.

Векторное хранилище используется как память системы. В него заранее загружается информация о структуре базы, примеры SQL-скриптов, описания бизнес-задач и дополнительные пояснения. Когда пользователь задает вопрос, система находит наиболее похожий контекст и передает его LLM, чтобы модель сгенерировала более точный SQL.

## 2. Какую информацию можно хранить в vector store

В нашем случае vector store может хранить несколько типов полезной информации.

### DDL-схемы таблиц

Это SQL-описания таблиц: имена таблиц, имена колонок, типы данных и комментарии к полям. Для экспериментов мы используем непрозрачные имена колонок, например `c01`, `a02`, `t05`, поэтому комментарии особенно важны. Без них модель не сможет надежно понять, что означает конкретное поле.

Пример: таблица операций содержит номер счета, сумму операции, канал операции, регион и дату. Если эти поля называются непрозрачно, то именно комментарии объясняют модели бизнес-смысл колонок.

### Документация по базе данных

Это короткие текстовые пояснения, которые не являются SQL-кодом, но помогают модели понимать предметную область. Например:

- какие таблицы описывают клиентов;
- какие таблицы описывают счета;
- где лежат транзакции;
- как соединять клиентов со счетами;
- как соединять счета с операциями;
- что означают статусы, типы счетов и роли клиента по счету.

Такая документация полезна, потому что пользователь обычно формулирует вопрос бизнес-языком, а не языком таблиц и колонок.

### Пары «описание задачи — SQL-скрипт»

Это основной материал для поиска похожих запросов. Каждая пара состоит из описания аналитической задачи и SQL-кода, который ее решает.

Например:

```text
Описание: Скрипт для поиска последних расходных операций клиентов по счетам за выбранный период.
SQL: SELECT ...
```

Такие пары позволяют системе находить уже решенные похожие задачи. Если новый вопрос пользователя близок к одному из сохраненных описаний, Vanna может использовать найденный SQL как пример.


## 3. Как работает поиск

Поиск работает как семантическое сопоставление текста пользователя с заранее сохраненными материалами.

1. Пользователь задает вопрос на естественном языке.
2. Вопрос преобразуется в embedding — числовой вектор, отражающий смысл текста.
3. Vanna обращается к Qdrant и ищет ближайшие векторы среди сохраненных объектов.
4. Для поиска похожих SQL-примеров мы сохраняем embedding только по тексту вопроса или описания, а сам SQL кладем в payload.
5. Qdrant возвращает наиболее похожие пары «описание — SQL».
6. Эти пары можно использовать напрямую для поиска похожих скриптов или передавать дальше в генерацию.

Важная особенность: мы изменили стандартное поведение Vanna для `add_question_sql`. В стандартном варианте embedding строится по связке `Question + SQL`. В нашей версии embedding строится только по тексту вопроса или описания. Это делает поиск более честным: пользователь ищет по смыслу задачи, а не по совпадению с SQL-кодом.

## 4. Как работает генерация SQL

Генерация SQL — это процесс, где Vanna собирает релевантный контекст и передает его в LLM.

Общий алгоритм:

1. Пользователь задает вопрос, например: «Сколько в среднем в месяц тратится на покупки?».
2. Vanna ищет похожие пары «описание — SQL» в vector store.
3. Vanna ищет релевантные DDL-схемы таблиц.
4. Vanna ищет релевантную документацию по базе.
5. Из найденного контекста формируется prompt для LLM.
6. LLM генерирует SQL-запрос.
7. Сгенерированный SQL можно выполнить в подключенной SQLite-базе.

Таким образом, модель не пытается угадать структуру базы с нуля. Она получает подсказки: какие таблицы есть, какие поля что означают, какие похожие задачи уже решались и какие SQL-запросы для них использовались.

## 5. Роль DDL, документации и SQL-примеров в генерации

Разные типы данных в vector store решают разные задачи.

DDL помогает модели понять физическую структуру базы: таблицы, поля и типы данных.

Документация помогает понять бизнес-смысл: что такое клиент, счет, операция, роль клиента по счету, связь между счетами.

SQL-примеры помогают модели понять стиль запросов и типовые паттерны: как соединять таблицы, как считать агрегаты, как фильтровать транзакции, как работать с датами.

Вместе эти источники снижают риск того, что модель придумает несуществующую таблицу, неправильно соединит данные или выберет не те поля.


## 6. Контроль безопасности при генерации

При генерации SQL важно не выполнять произвольный код от модели. Поэтому в нашем Vanna-клиенте добавлена проверка промежуточных SQL-запросов.

Если LLM просит выполнить промежуточный запрос для уточнения данных, система разрешает выполнять только read-only SQL, то есть безопасные `SELECT`-запросы. Запросы типа `DROP`, `DELETE`, `UPDATE`, `INSERT` не должны выполняться.

Это снижает риск случайного изменения или удаления данных при работе с моделью.

## 7. Как используется подготовленный датасет

Для экспериментов мы готовим несколько артефактов:

- SQLite-база с тестовыми банковскими данными;
- DDL-схемы с комментариями;
- текстовое описание схемы с примерами первых строк;
- CSV-файл с описаниями аналитических задач;
- сгенерированные SQL-скрипты;
- результаты выполнения SQL-скриптов.

Эти артефакты нужны для двух направлений:

1. Оценка поиска: насколько хорошо система находит релевантный SQL по описанию задачи.
2. Оценка генерации: насколько корректный SQL модель создает по вопросу пользователя и найденному контексту.

## 8. Итоговая схема работы

Упрощенно процесс выглядит так:

```text
Пользовательский вопрос
        ↓
Embedding вопроса
        ↓
Поиск похожих DDL, документации и SQL-примеров в Qdrant
        ↓
Формирование prompt для LLM
        ↓
Генерация SQL
        ↓
Проверка и выполнение SQL в SQLite
        ↓
Результат для пользователя или сохранение для оценки качества
```

## 9. Практическая ценность

Такой подход позволяет постепенно накапливать корпоративную SQL-память. Каждый проверенный SQL-скрипт с хорошим описанием становится новым примером для будущего поиска и генерации.

Для бизнеса это означает:

- быстрее находить уже существующие аналитические решения;
- снижать зависимость от знания конкретных таблиц и полей;
- помогать пользователям формулировать запросы на естественном языке;
- ускорять подготовку SQL для типовых аналитических задач;
- экспериментально измерять, какие форматы описаний и комментариев дают лучшее качество.

На текущем этапе проект является исследовательским прототипом. Главная задача — понять, какие виды контекста в vector store лучше всего помогают Vanna находить похожие SQL-скрипты и генерировать корректные запросы к базе.
